Where a save can lie

“Save failed” does not always mean the old file survived. Inspect the boundary before choosing a retry policy.

Finding 01 · recovery semantics

The replacement is already visible

Trigger: the file replacement succeeds, then syncing the containing directory fails. The user sees an error even though the new journal is visible.

fs::rename(&temp, self.root.join("board.json"))?;
replaced = true;
hook(Stage::AfterReplace)?;
File::open(&self.root)?.sync_all()

Exact excerpt from Store::save_with. The flag changes before directory durability is confirmed.

Consequence: blind retry can misrepresent whether the previous attempt committed. Report uncertainty and inspect/reopen before deciding.

The two sides of the boundary

Before replace

Write or file sync fails

Old committed file remains

Staging bytes are not recovery candidates.

After replace

Directory sync fails

New file visible; durability uncertain

Do not promise rollback.

Finding 02 · checksum is not trust

The SHA-256 detects mismatched journal bytes; it is unkeyed and stored beside the data. An actor able to rewrite both can recompute it. Treat a matching digest as integrity checking, not authentication.

Finding 03 · another writer is a real boundary

Store::open acquires an OS-backed single-writer lock. A second session does not silently merge changes. Do not design an autosave UI as though arbitrary concurrent writers are supported.
