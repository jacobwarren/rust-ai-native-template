What the implementation taught us

A retrospective study of the existing store—not a fabricated live log. New tasks must write these observations when they occur.

This example demonstrates how to explain discoveries. The entries below reconstruct actual source semantics; they do not assert when the original author discovered them.

Boundary discovery

A failed save can still replace the file

Initial model to challenge: any save error preserves the old committed bytes.

Observed code: Store::save_with sets replaced=true immediately after rename, before directory sync. The error mapping returns save_uncertain after this point.

Conservative decision: distinguish visibility from durability in the proposed UI. Do not auto-retry uncertain results.

Impact: the plan's after-replacement scenario needs a distinct state and acceptance expectation. Storage tests are the relevant product evidence; this page itself is not an executed test.

Recovery constraint

Staging files are never recovery candidates

Observation: load reads board.json only. A leftover .tmp file does not become current merely because it is newer.

Decision: the recovery assistant proposal must inspect the committed pathname. Avoid a “recover newest file” shortcut.

Next uncertainty: how to communicate uncertain durability in a future graphical interface remains a design decision, not a missing storage implementation.

Carry into the next attempt

  • Separate visible replacement from confirmed directory sync in the first mental model.
  • Preserve the exact error distinction through presentation layers.
  • Test recovery promises independently from appearance and from the artifact simulation.
