Three rules the diff does not spell out

        
Each one decides what an agent sees for an input nobody tested.


        

          
01The scan stops at the first --, and command words stop at the first flag

          

            
What
requested cuts the arguments at the first --. If any word before that cut is exactly --help or -h, no arm runs. Only the words before the first word that starts with - count as command words. narrowed then prints every entry whose usage starts with those words. (help.rs:135-159, main.rs:81-85)

            
Why
The arms ["check", profile], ["workflow", id] and ["release", scope, ...] bind any word in that slot, so on main check --help asked for a profile named --help. A scan inside the match would come too late. Words after -- belong to the starter app.

            
Cost
A value that is exactly -h counts as a help request. task-artifact verdict … --notes -h now prints verdict's entry and records nothing (captured, exit 0). Notes like that have to go through --notes -.

          

        


        

          
02Usage keys are read by a matcher, so how a key is spelled changes behaviour

          

            
What
A key splits on spaces and drops [ ]. An all-UPPERCASE token (ID, SCOPE, ARGS...) is a placeholder and matches any word that does not start with --. Any other token matches only itself, and a|b matches either. Five of main's keys were respelled to this rule, for example workflow [id] became workflow [ID] (compare git show main:xtask/src/main.rs).

            
Gap
every_key_reads_as_a_usage checks which characters each token uses, not what the token was meant to be. A lowercase word meant as a placeholder passes it. The integration tests pin the spelling of workflow [ID] and release SCOPE --report PATH, and nothing pins a key added later. (help.rs:188-216, test at help.rs:222-243, tests/help.rs:35-41)

          

        


        

          
03Wrong arguments get the usages under the longest matching prefix, on one compact line

          

            
What
usage_error tries every typed word, then one word fewer each time, until some usage starts with them. The error names only the typed words that matched literal command words, so release myscope says "wrong arguments for release". It adds "flags go in the order shown" only when a matched usage has a --name flag. If not even the first word matches, the reply is "unknown command WORD; run cargo xtask help" with no usage array. (help.rs:100-131, 161-186, main.rs:251)

            
Why
The arms still match fixed slices, because the interview kept the hand-written match, so that order clause is the one rule an agent cannot see. Successful replies print pretty, so their first line is { (main.rs:29). Errors stay on one line (main.rs:43-53). That is because the stop hook reads exit 1 with a first line of exactly { as the gate's verdict, and reads anything else as "could not run" (agent-complete.sh:77-78).

            
Gap
Only a comment holds that one-line shape (main.rs:44). In a scratch copy with errors pretty-printed, every cargo test -p xtask binary still passed.

Existing structure this leans on

          The match arms in dispatch and TABLE are kept in step by hand. The match decides whether a command runs. TABLE decides what its help and its usage errors say. Nothing checks that every arm has an entry, or that every entry has an arm. Today they agree. Table-driven dispatch would close the gap, and the interview left it out of scope.
