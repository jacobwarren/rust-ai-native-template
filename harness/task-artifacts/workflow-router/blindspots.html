Unknown unknowns: tickets, the skill carve-out, next and the verdict log

Seven things in xtask/src/, scripts/agent-hook.sh and the agent folders that the plan doesn't mention yet. Each one comes with the code or command output that shows it. Untick a finding to leave it out of the prompt at the bottom, and pick an answer to the three open decisions.

The prompt
I'm about to add a ticket-writing skill, carve .claude/skills/ out of the protected paths so ordinary skills can be small tasks, and add a task-artifact next command with a structured review-verdict log to this Rust harness template's xtask gate, guard and skills. Do a blindspot pass: find my unknown unknowns in this part of the codebase, explain each one with the code that proves it, and tell me how to prompt you better for the implementation.
What you asked for

Four tidy additions: a thin skill, a one-line change to a path table, a router command that reads files, and a JSON log. Each looks like a few dozen lines.

What you're actually walking into

A skill folder that can register hooks and pre-approve tools, a parity test that can't see an exception list, a size limit that counts every skill twice, a branch whose default base gives the wrong answer, and two shipped tasks whose prose verdicts already show pages edited by hand after their last review.

The blindspots

Landmine01

A Claude Code skill isn't only prose: the carve-out lets a change with no receipt register hooks and pre-approve tools

Today every file under .claude/ is a policy path because of one prefix in PROTECTED_PREFIXES (transitions.rs:39-47, matched in protected() at 62-64). The agent-workflow blindspot pass recommended the carve-out on the grounds that "skills are documentation". Claude Code's skill frontmatter says otherwise. A SKILL.md may declare:

# Claude Code docs, Skills, frontmatter reference
hooks:          "Hooks that Claude Code registers when the skill is invoked and
                 keeps running for the rest of the session."
allowed-tools:  "Tools Claude can use without asking permission during the turn
                 that invokes this skill."
!`command`      "runs shell commands before the skill content is sent to Claude"
                 (injected commands never prompt while the skill renders)
context: fork + agent:   runs the skill as a subagent of a named type

The repository's own hooks live in .claude/settings.json, and changing them needs a receipt. After the carve-out, the same hook declared in a new skill's frontmatter needs no receipt, and a small task could add it. One thing doesn't change: Claude Code itself still lists .claude as a protected directory and prompts before writes there in default and acceptEdits mode. Allow rules can't pre-approve that prompt. The carve-out removes the harness receipt but leaves the host's prompt in place.

Why it bites"Ordinary skills can be small" becomes "any skill can be small". A session-long hook or a Bash pre-approval would then reach main with no policy rationale, on a path the guard no longer flags.
Landmine02

The parity test compares two named variables, and an exception list kept in one place still passes it

Both tables are prefix lists. The Rust side uses path.starts_with(p), and the shell's tier() uses case "$p" in "$x"* (agent-hook.sh:137-144). ".claude/ except skills/" can't be written as a list entry. It needs a third list or a code path in each place. guard_tiers_match_protected_paths (transitions.rs:221-225) finds the lines that start PROTECTED_PREFIXES=" and PROTECTED_FILES=" in the script and compares only those. I applied the carve-out to protected() alone and ran:

$ cargo test -p xtask guard_tiers_match_protected_paths
test result: ok. 1 passed; 0 failed
$ echo '{"tool_name":"Edit",…".claude/skills/write-ticket/SKILL.md"}' | scripts/agent-hook.sh guard claude
".claude/skills/write-ticket/SKILL.md is a protected policy file. This branch
 will need a transition receipt: run cargo xtask gaps --base origin/main before completion."

The existing tier test (tests/tiers.rs:137-158) checks that ceremony paths force standard, and the narrowed list still passes it. No test checks that an ordinary skill doesn't force standard, or that .claude/settings.json and .claude/agents/ still do.

Why it bitesIf the two tables drift one way, the guard tells agents to write receipts the gate never asks for. If they drift the other way, the guard stays silent and the gate demands a receipt at completion. Either way the test stays green.
Convention03

Every skill is written twice, so even after the carve-out a skill-only small task tops out near 50 lines

The agent-workflow pass established why skills are byte-identical copies in .claude/skills/ and .agents/skills/ instead of a symlink: repo::files errors on any symlink (repo.rs:39-45), and DOC007 holds the copies equal (checks.rs:186-206). The new consequence is that size.rs counts both copies against the 100-line limit (SMALL_LINES, line 9; check_small, 87-114). With the carve-out applied and a new skill on a small-tier record:

60-line SKILL.md in both hosts:
task tier small: 120 changed lines exceed the small limit of 100
50-line SKILL.md in both hosts:
(no tier error)   # docs.json entries (DOC004) are administrative and don't count

For scale, the skills here are 40, 54 and 71 lines (add-product-command, author-artifact, review-artifact), and your doppel-ticket is 92 lines, symlinked between ~/.claude/skills and ~/.agents/skills, which this repository refuses. Edits to an existing skill will usually fit. Adding a skill of normal length won't.

Why it bitesThe ticket skill ships inside this standard task, so it isn't affected. The goal of letting ordinary skills be small tasks is affected: it delivers less than it sounds like, and the first person to add a 60-line skill will be refused with an error about line counts, not about mirroring.
Missing concept04

next can see what's committed, but not where the branch starts or when the code is finished

guard() only asks whether the discovery pages are in HEAD's tree (artifacts.rs:199-225). The rules next has to steer by live in order() (157-197), and they depend on two things a history read doesn't give it. The first is a base, which sets which commits belong to this branch (history::commits, base..HEAD, first-parent). This branch is stacked on PR #3, and the Stop hook defaults to HARNESS_BASE=origin/main (agent-complete.sh:23). With five discovery pages, one code commit and the final pages committed on top of this branch:

$ xtask handoff --base origin/main
task HTML artifact: blindspots.html must be committed before the first product-code commit
  # PR #3's 18 commits count as this branch's code
$ xtask handoff --base origin/harness/agent-workflow
(no artifact error)

The second is the last product-code commit, which is only known in hindsight. Notes must land before it (line 183), and buy-in and quiz must be touched at or after it (189-195). If a quiz review leads to one more code fix, both final pages have to be touched again. Notes committed after what turns out to be the last code commit fail. With a single code commit, the notes may share that commit but can't come after it. If PR #3 is squash-merged, its original commits stay in this branch's main..HEAD, so the branch needs a rebase before the default base is right.

Why it bitesA router that guesses the base or infers "done" from history will confidently send the agent to the wrong page. That's the same drift the command is meant to remove, now with the authority of a tool behind it.
History05

The verdicts you want to log already exist as prose, and they describe exactly the drift a PASS/REVISE row can't capture

Verdicts are recorded today as free text in review.verification. The two completed standard tasks say:

# harness/tasks/agent-workflow.json
"implementation notes reviewed REVISE on wording only, fixed by hand and not re-reviewed;
 buy-in REVISE on two ungrounded claims, reworded by hand and not re-reviewed"
"interventions committed as best after two rewrites" · "final finding checked and found mistaken"
# harness/tasks/default-hooks.json
"interventions, interview, reference and plan committed as best after two rewrites"
"updated the notes, buy-in and quiz pages by hand; those edits were not re-reviewed"

Across those 16 pages, 6 were committed as the best version after two rewrites, and 5 carry hand edits made after their last review. A row of {page, round, verdict, findings, model} can't show that the committed page differs from the page that was judged. The repository already has a pattern for that: a receipt's Change binds before_sha256 and after_sha256 (transitions.rs:14-20), and receipts are append-only (105-113).

Why it bitesWithout a page hash, the log reports "quiz: PASS" for a quiz that was rewritten afterwards. That's the auditable trace the owner asked for, recording the opposite of what happened.
Landmine06

Where the log lives decides who can write it and when it makes your CI evidence stale

harness/task-artifacts/ID/reviews.json is the natural spot. It's administrative (artifacts.rs:33-43), so it never counts toward a small task's size. The page checks ignore it, because check_written names its eight pages and screenshots takes only .html (231-235). Three other effects come with that folder:

$ echo '{"tool_name":"Write",…"harness/task-artifacts/workflow-router/reviews.json"}' \
    | scripts/agent-hook.sh author claude
{}   # allowed: the author hook admits any file under harness/task-artifacts/<task>/ (line 402)
$ xtask env | grep source        # before and after writing reviews.json
  "source_sha256": "e723e390…"
  "source_sha256": "88f06c6a…"

So the page author can write its own verdict, while the reviewer has no Write or Edit tool at all (.claude/agents/artifact-reviewer.md). Whatever lands in the log is the orchestrator's transcription. The fingerprint covers every file outside .git, target and a few host-local paths (repo.rs:20-71). A verdict recorded after check ci therefore fails completion with "complete task requires current full-CI evidence" (completion.rs:62-68), which is also true of review.verification today. An uncommitted log blocks completion (committed(), 141-155). A shared file such as harness/reviews.json wouldn't be administrative, so every verdict would count as product lines.

Why it bitesThe log exists to stop agents from grading their own work, and the folder it would sit in is the one folder the author agent is allowed to write.
Convention07

A doppel-style ticket has five sections, and the task record has a slot for about one of them

Task is deny_unknown_fields (task_record.rs:26-45). It has summary, requirements, remaining, related_gaps, tier and an opaque work_item (COMPLETION.md, lines 5-6), but no field for acceptance, validation or out of scope. requirements are ids from harness/readiness.json, of which there are six coarse ones (driver, state, persistence, evidence, completion, task-artifacts). A complete record must name at least one (line 113), and each must be verified by current CI (completion.rs:69-80).

doppel-ticket's core rule is "acceptance criteria are tests, named". Here a named test counts toward the gate only if it's listed under a requirement in readiness.json, and that file is protected (transitions.rs:50). A ticket whose acceptance adds a gate-visible test is therefore a standard task by construction. The word "small" collides too. doppel's small is one to three production files plus a test file, while the harness's small is 100 changed lines in total, tests included, with no Cargo.toml, protected or ceremony path. The tier also can't be changed once code lands, as the agent-workflow pass showed.

Why it bitesA ticket skill that copies doppel's headings will mark tickets "small" that the gate refuses. It will also invent record fields that serde rejects, or acceptance tests the gate never sees.
