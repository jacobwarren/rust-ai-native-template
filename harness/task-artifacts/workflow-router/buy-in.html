02Why ship it

The page loop had rules and nothing that applied them. In the last two tasks the orchestrating agent ran it from prose and drifted: it edited pages after their final review, committed pages before their review finished, and applied the rewrite rule unevenly; 5 of the last 16 pages were edited after their final review (blindspots, B05). Verdicts were free text in the task record, so no one could tell which version a reviewer saw or how often a page type needs a rewrite. Now the loop's state is data a command reads, and every verdict names the bytes it judged. The stacked-branch fix came out of this task's own refused stops and serves the next stacked branch. CI is unchanged.

03What approvers will ask

Can next or the log block a task?
No. next always answers ok: true and exits 3 when it has advice, an exit code new to xtask (xtask/src/main.rs). verdict refuses only malformed rows.
Can an agent fake a verdict?
Not with its Edit or Write tools (case 5). Rows are committed beside the pages they judge, so a forged one shows in history.
Does the stop change let a branch skip its checks?
Only at stop, and only for commits another remote branch holds. PR CI still judges every record against the PR's base. The gaps are in section 06.

06Known limits, and what the owner decides

  • Advice only. Nothing stops an agent that ignores exit 3 or never runs next; a hand edit after review is flagged, not refused.
  • Shell writes to the log are unconfined. The author hook covers Edit and Write only, and Codex roles have no write limit; a forged row shows in Git history.
  • Order breaches show only at completion. next takes no base, so code before the discovery pages draws no advice (open gap artifact-gate-holes).
  • Some pushes hide a branch's own commits. A copy pushed under another name, a branch pushed on top, or a detached HEAD at a pushed commit: the stop then judges only later commits and uncommitted records. PR CI judges them all (docs/COMPLETION.md).
  • A squash-merged, deleted lower branch is judged again. Its commits stay in this branch's history but no remote branch holds them, so the stop judges the lower record again, the old behaviour. Rebasing onto main, or HARNESS_BASE at the lower branch's old tip, clears it (quiz, run in a fixture).
