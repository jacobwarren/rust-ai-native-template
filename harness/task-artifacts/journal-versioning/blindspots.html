Versioning the saved-board journal: what you don't know yet

The prompt
I'm about to version the saved-board journal format in the engine's persistence layer (crates/engine, starting from crates/engine/src/store.rs) so we can add new journal commands without stranding boards people have already saved, and so older builds refuse newer files clearly. Do a blindspot pass: find my unknown unknowns in this part of the codebase, explain each one with the code that proves it, and tell me how to prompt you better for the implementation.
What it sounds like

The file already carries schema_version: 1 and load already rejects anything else. Bump the number, add a match arm for v2, add the new command variant, done.

What you are walking into

A reader that parses every command strictly before it looks at the version, a checksum computed over today's Rust types rather than the file's bytes, one Command enum that is wire protocol, capture output and file format at once, and a test suite that has never seen a file it did not just write.

The blindspots


  
  

    
Landmine01
      
The version check is unreachable for almost every real "newer" file

    
load deserializes the whole file into today's strict types first, and only then compares schema_version. Envelope and Journal deny unknown fields, and Command is an internally tagged enum that also denies unknown fields. So a newer file with a new command, a new field on an existing command, or a new envelope field fails at line 127 with invalid_store. The version error at line 129 only fires when the newer file happens to be shaped exactly like v1.

    
    
In the probes, a v2 file containing rename came back as invalid_store: unknown variant `rename`, expected one of `add`, `complete`, `remove`, `undo`. Of the four v2 files, only the one with nothing new in it produced version.

    
Why it bitesThe build people have today is the "older build" in your goal, and its code is already frozen. No file a v2 writer produces can make it say version once a new command is in the journal. "Refuse newer files clearly" is achievable only for builds that ship with this change, and only if the new reader reads the version before it parses commands. Bumping the number alone repeats today's ordering in the next build.

    
Read schema_version with a lenient probe (only data.schema_version, unknown fields ignored) before any strict parse, and refuse newer versions there. Add a test with a newer file that contains an unknown command and assert the version error, not invalid_store.

  


  
  

    
Landmine02
      
The checksum covers today's Rust struct, not the bytes on disk

    
Both save and load hash serde_json::to_vec(&Journal). On load that is the parsed and re-serialized value, so the digest is defined by the field order and serde attributes of the types you load into. Whitespace and key order in the file are irrelevant: a pretty-printed file with keys reversed loads fine. A writer that hashed {"commands":…,"schema_version":1} in that order is rejected as corrupt_store, although its content is identical.

    
    
Why it bitesThe natural v2 move is to widen the types: add a field to Journal, give Add an optional field, reorder Journal's fields, then load v1 files into those wider types. Each of those changes what re-serialization produces, so every intact v1 board would fail with corrupt_store. That is the worst outcome for the "don't strand saved boards" goal, and it reports a healthy file as damaged.

    
Verify each file's sha256 against the serialized form of that version's own frozen types, before any migration. Never re-hash a v1 file through v2 types. Keep v1's field order (schema_version, commands) and serde attributes byte-identical.

  


  
  

    
Missing concept03
      
A saved board is a list of intents, re-judged by today's rules every time it opens

    
The file stores commands, not tasks. load hands them to Session::replay, which runs each one through execute on a fresh session, including title validation and the undo history. In the probes, a v1 file with title "  Review  " opened as "Review", and a v1 file whose second command completes a missing task was refused as replay_failed: step 1: task does not exist.

    
    
Undo is rebuilt the same way: every non-undo command pushes the prior board (lib.rs:82–86), so a new command is undoable after reopen automatically, whether or not you want that.

    
Why it bitesA schema version protects the file's syntax. It does not protect its meaning. Tighten a title rule in board.rs, lower MAX_TASKS, or change what undo restores, and a perfectly valid v1 file can stop opening or open as a different board, with no version change involved. You need to decide whether the version number promises meaning too.

    
Treat replay semantics as part of compatibility: a checked-in v1 board must replay to the same inspect state in every future build. State in the plan whether the new command is undoable and how replay handles it.

  


  
  

    
Landmine04
      
One Command enum is the wire protocol, the capture format and the file format

    
The same type is deserialized from execute and replay requests, returned by capture as journal, and stored in board.json. Adding a variant for the file changes the driver protocol in the same commit. Yet protocol_version is a literal 1, and the discovery list is hand-written, so a new variant can be accepted by execute while discover never mentions it.

    
    
    
Why it bitesA journal captured from a v2 build and fed to an older build's replay fails as invalid_request, another unversioned path for the same data. If you keep v1 decoding on the shared enum, you can never change how an existing command serializes on the wire without breaking v1 files (see 02). The architectural choice is whether the stored format gets its own frozen type. That is decision A below.

    
List every place Command crosses a boundary (execute, replay, capture, board.json) and say for each whether the change is visible there. Make capabilities() cover every variant with a test that fails when one is missing.

  


  
  

    
Convention05
      
New commands must be struct variants. A unit variant silently accepts junk

    
Undo {} looks odd for a command with no data. It is deliberate: docs/DRIVER.md says unknown fields fail "including empty-struct variants", and tests/protocol.rs:45 rejects {"command":"undo","id":1}. I checked serde 1.0 directly with the same attributes: Undo {} rejects that input with "unknown field `id`", while a unit variant Undo accepts it.

    
    
Why it bitesA no-argument command written as a unit variant compiles, passes round-trip tests, and quietly ignores misspelled fields in requests and in stored files. That breaks the strictness that 01's version probe and 02's checksum rely on.

    
Any new Command variant without data is written as Name {}, never a unit variant. Add the new command's typo case to strict_requests_and_nested_commands_fail_without_mutation.

  


  
  

    
Landmine06
      
The first save from a new build upgrades the board one way, with no copy kept

    
save always rewrites the whole journal under a version literal and renames over board.json. load never writes. So a v1 board is still v1 after a v2 build opens it, but becomes whatever the writer stamps on the next save, even if nobody used a new command. docs/DRIVER.md is explicit that there is no automatic backup archive.

    
    
Why it bitesIf the v2 writer always writes 2, anyone who opens and saves a board in the new build can no longer open it in the old build, even though the journal contains nothing the old build doesn't understand. Writing the lowest version that can express the journal avoids that. Decision B below.

    
Decide the writer rule explicitly (lowest sufficient version vs always newest) and test it: open a v1 board in the new build, save without new commands, and assert the schema_version on disk.

  


  
  

    
Test gap07
      
No test has ever loaded a file this build did not just write, and the future-file test only asserts is_err()

    
Every store test creates its file with the current store.save. The goldens in harness/goldens/ are inspect states, not board.json bytes. After you change the writer, the round-trip tests read what the new writer wrote and stay green, even if v1 files no longer load. The only "future" case bumps the number to 999 on an otherwise v1 file and accepts any error.

    
    
Why it bitesThis test passes today for version, and would pass equally for invalid_store or corrupt_store. It cannot tell a correct refusal from 01's wrong one. crates/engine/AGENTS.md also says golden files need explicit review and never auto-create, so the v1 fixture has to be written down from real v1 bytes, not regenerated by the new writer. Before changing the writer, check in the exact v1 bytes as a reviewed fixture and assert it loads to tasks [{id 1, "Review", done false}], next_id 2, revision 3, can_undo true. Make the corrupt/future test assert exact error codes.

  


  
  

    
Convention08
      
The version error code already means "bad request version", and the message names no numbers

    
The driver rejects a request with schema_version: 2 using the same code, version, that the store uses for a newer file. A client can only tell them apart by message text. Neither message says which version it found or which it supports. The version is also checked before the checksum, so a damaged version field is reported as "unsupported version" rather than corruption. Load error codes are not listed in docs/DRIVER.md, and the 1 lives as two separate literals (store.rs:80 and :128).

    
    
Why it bites"Refuse clearly" is mostly about what the user reads. Today's message can't say "this board was saved by a newer build (format 2); this build reads up to 1". A shared code also makes "update your app" advice ambiguous between a client problem and a file problem. Decision C below.

    
Give the newer-file refusal its own error code with found and supported versions in the message, keep it out of the protocol's version code, and document every load error code in docs/DRIVER.md.
