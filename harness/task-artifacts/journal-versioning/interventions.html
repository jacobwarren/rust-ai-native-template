Where we could intervene so a new command can't strand saved boards

Eleven places, cheapest first, each grounded in the persistence path as it exists today. Check the ones that resonate; the table near the end shows what your picks would change, and the bar at the bottom builds your reply.

The prompt
“Here's the problem: we can't add a new journal command (for example, renaming a task) to saved boards without risking the boards people have already saved, and a build that meets a board saved by a newer build should refuse it clearly instead of failing confusingly or damaging it. Search the codebase and brainstorm the places we could intervene, from cheapest to most ambitious. I'll tell you which ones resonate.”

What the search turned up

I read crates/engine/src/store.rs, the Command and Session types in crates/engine/src/lib.rs, the driver in protocol.rs, the store tests and the board workflows, then forged newer-format files and fed them to today's driver. The pattern: a version number already exists and is already checked, but it is checked too late, on the read side only, and the thing it versions is the public command enum. The cheap options are mostly reordering and tightening, not building.

The version is read after the commands are parsed.

serde_json::from_slice::<Envelope> at store.rs:127 decodes every command with deny_unknown_fields before the schema_version != 1 check at :128 runs. A newer file usually dies on its new content, not its number.

Save never looks at what it replaces.

save_with builds schema_version: 1 (store.rs:79-82), stages a temp file and renames it over board.json (:100). No read of the existing file happens anywhere on that path.

The file format is the wire format.

Journal.commands is Vec<Command> (store.rs:14), the same enum the driver accepts for execute and replay (protocol.rs:23-24). Adding Rename changes the file, the request protocol and captured journals in one stroke.

How load works today, and where a newer board exits

Save path: build Journal { schema_version: 1, .. } → checksum → write temp → fsync → rename over board.json → fsync dir (store.rs:73-114). Nothing on this path asks what version the file being replaced was.

What today's build does when it meets a newer board

I saved a real board with today's driver, then wrote variants with correct checksums the way a future build plausibly would, and ran load against each with APP_DATA_DIR pointed at a scratch directory. Today's build plays the part of “the older build”.

#1

Read the version before parsing the commands

S
crates/engine/src/store.rs:127-129 · Store::load

FoundThe only version check sits behind a full strict decode. In the probe, a v2 board containing a rename never reached it: the error was invalid_store with a serde message about an unknown variant, which reads like a corrupt file. Decode a lax peek first, with no deny_unknown_fields and the commands ignored, check the number, then do the strict decode.

#[derive(Deserialize)] struct Peek { data: PeekData }
#[derive(Deserialize)] struct PeekData { schema_version: u32 }  // other fields ignored

ImpactA newer board is refused because of its number, whatever new commands or fields it carries. The created_by probe shows the peek must ignore unknown fields at both levels, or a future envelope change brings the confusion back.

WatchThis only protects builds that contain it. Builds already in people's hands will keep saying “unknown variant `rename`”, so the reader fix has to ship in a build before the one that adds rename.

#2

Give “board is too new” its own code and both numbers

S
store.rs:129 · protocol.rs:68 · store_tests.rs:98-119

FoundThe store refuses with code version and the message “unsupported saved journal version”. The driver uses the same code version for “unsupported protocol version” on a bad request (protocol.rs:68), so a client can't tell “your request is wrong” from “your file is from the future” without parsing English. Neither message says which version was found or which this build reads. The existing test feeds a version-999 file and asserts only is_err() (store_tests.rs:116), so the code is unpinned.

ImpactSomething like store_too_new: “board.json uses journal format 2; this build reads up to 1. Open it with a newer build. The file was not changed.” The last sentence is true today because load never writes, and it's the sentence that stops a user from deleting the file. Tighten the test to assert the code.

#3

Accept every version up to ours, not just ours

S
store.rs:128 · store.rs:79-82 · store.rs:131

FoundThe check is equality: schema_version != 1. The obvious edit when adding rename, bumping both the writer at :80 and this check to 2, would refuse every board saved before the change. Because Rename is additive, every v1 command decodes unchanged under the new enum, so 1..=2 is the whole migration for this change.

ImpactOld boards open in the new build with no conversion code. The checksum survives too: the probe shows it is computed by re-serializing the parsed struct (:131), so as long as Journal keeps its shape and the read schema_version is kept as read, a v1 file hashes the same.

WatchThat same detail is a trap later. Add any field to Journal and re-serialization emits it, so every older file fails with corrupt_store. That's when you need #9.

#4

Commit a v1 board and make every build load it

S
store_tests.rs:36-49 · harness/goldens/*.json

FoundNo test reads bytes written by an earlier build. The store round-trip test saves and loads with the same code (store_tests.rs:36), and the three goldens are inspect snapshots selected by /result/snapshot, not files on disk. The exact bytes today's build writes are short enough to check in:

{"data":{"schema_version":1,"commands":[{"command":"add","title":"Review"},{"command":"complete","id":1}]},"sha256":"cd128a02…714c4"}

Impact“Don't strand saved boards” becomes a failing test instead of an intention. It also catches the quieter risk: load replays raw titles through current rules (lib.rs:107), so tightening Title later would strand boards too. Add an undo and a raw " Review " title to the fixture so both paths are pinned. crates/engine/AGENTS.md already requires goldens to be reviewed and never auto-created.

#5

Refuse to save over a board this build can't read

M
store.rs:73-114 · Store::save_with

FoundThis is the “damaging it” half of the problem, and it already happens. In the probe, load failed on the v2 board, the session stayed empty and still editable, one add and one save later the newer board was replaced by a one-task v1 board, and save answered ok: true. Before staging, peek at the existing board.json (reusing #1's peek) and refuse with the same too-new code if its version is above ours.

ImpactThe only option that protects a newer board from an older build after a failed load. The single-writer lock (store.rs:56) already rules out a race between the peek and the rename.

WatchIt forces a policy call: what about an existing file that is corrupt or unparseable, rather than newer? Today saving over it is the only in-app recovery, and DRIVER.md promises load never silently swaps in empty state but says nothing about save. The M is for that decision, not the code.

#6

Write the lowest version the content needs

M
store.rs:79-82 · lib.rs:30-37

FoundThe writer hardcodes schema_version: 1. If it instead wrote 2 only when the journal actually holds a rename, a board that never used rename would stay a v1 file. The probe's “v2, add only” row, refused today, would simply open in an older build.

ImpactDowngrade keeps working for most boards, and each future command declares the minimum format it needs in one function next to Command.

WatchUndo doesn't remove entries: execute pushes every command, undo included, onto the journal (lib.rs:88). Rename a task, undo it, and the board looks unchanged but is a v2 file forever. That is correct, but someone will report it as a bug.

#7

Freeze a stored command type apart from the wire Command

M
store.rs:14 · lib.rs:30-37 · protocol.rs:23-24, 32-43

FoundCommand's serde attributes (tag = "command", rename_all, deny_unknown_fields) define both the request protocol and the file. Any wire-only change, such as an optional field on add or a renamed tag, silently becomes a file-format change with no version bump. A StoredCommand enum owned by store.rs, converted with an exhaustive From, makes every format change a visible edit to the store module.

ImpactThe file stops moving when the protocol does. The exhaustive conversion is also a compile-time reminder to decide each new command's format version, which pairs with #6.

WatchNot every match will remind you. Session::execute matches exhaustively (lib.rs:56), but the property test's reference model ends in _ => false (tests/properties.rs:59), so Rename compiles there untested.

#8

Version captured journals and replay requests too

M
protocol.rs:33, 87-95 · docs/DRIVER.md (capture, replay)

Foundcapture returns "journal": session.journal() with no version, and replay accepts a bare Vec<Command>. That makes captures a second, unversioned saved format that people keep as evidence and feed back in. In the probe, a replay containing a rename failed as invalid_request with id: null, so the caller can't even tell which request failed. discover still reports protocol_version: 1.

ImpactAdd a journal_version next to the captured journal and accept it on replay, or bump protocol_version when rename lands. Once rename is listed in capabilities, the discovery test (tests/protocol.rs:12-21) requires its example to execute, so clients can feature-detect it from discover.

#9

Per-version decoders with an upgrade chain, hashing the bytes as read

L
store.rs:116-136 · Cargo.toml:16 (serde_json, no features)

FoundLoad has one shape, the current one. A version match lets each format keep its own struct: 1 => decode_v1(bytes)?.upgrade(), 2 => decode_v2(bytes)?. To stop #3's checksum trap, hash the data bytes as they appear on disk. That needs serde_json's raw_value feature, which isn't enabled today. The alternative is to always re-serialize through the struct of the version that was read.

ImpactNon-additive changes become routine. Storing normalized titles instead of raw input, or adding metadata like created_by, would be an upgrade step rather than a stranding event. Rename by itself doesn't need this.

#10

A workflow that runs two builds against one data directory

L
harness/workflows.json · xtask/src/workflows.rs

FoundThe workflow harness already runs multi-session process journeys. board-lifecycle covers “save, exit, reopen and undo with preserved history”, but every session runs the same binary. A cross-build workflow would build the base branch's starter-app in a worktree and check both directions. New saves, old loads: expect the too-new code with the file unchanged. Old saves, new loads: expect an identical snapshot.

ImpactThe only option that tests the actual promise between two real builds rather than forged files like the probe's. The cost is a second build in CI and a binary-per-session field in the workflow schema.

#11

Persist the board, not the commands

XL
store.rs:10-21 · lib.rs:39-44 · lib.rs:9-10

FoundThe file is a command log, so every new command and every tightened domain rule is a format question. Storing Board state instead would make rename format-neutral, since titles already exist, and stop re-validating years-old input on every load.

WatchUndo across reopen is a promised behavior: the board-lifecycle workflow reopens and undoes. Keeping it means storing history, up to 256 boards (MAX_COMMANDS) of up to 64 tasks each. At full size that's megabytes against the 256 KiB MAX_BYTES cap. So this needs history deltas or giving up undo after reopen. That's a product decision, not a refactor.
