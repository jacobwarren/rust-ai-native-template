Journal versioning · before code · reference map

What a saved board means today

A saved board is a program, not a picture. Store::save writes the command journal with a version and a checksum; Store::load parses it, checks it and replays it into a fresh session. No fixture, spec or test pins those bytes, so this code is the only definition a versioned format has to stay compatible with.

Today's Store::load and Store::save (crates/engine/src/store.rs) already behave the way versioned saved boards must keep behaving for every board saved so far. Read them and show me a semantics map, with matched excerpts, gotchas and edge cases, so I can confirm you understood exactly what versioning the journal format must preserve before you build anything.

1One version number, inside the checksummed data, always 1. The envelope has no version of its own and accepts no other key. discover's protocol_version: 1 (protocol.rs:33) is the request protocol, not the file.
2Commands are stored as admitted, and nothing derived is stored. " Zoë " keeps its spaces because execute journals the command it was given (lib.rs:88); only replay trims. Undo is an entry like any other. Ids, done flags and next_id are not in the file. The same Command enum also defines execute, replay and capture (protocol.rs:23-24, 94), so a new variant changes all four at once.
3The hash covers serde's compact output of this private struct, in declaration order. Whitespace, key order and escapes in the file do not matter, because load re-serializes before hashing. The Rust field order and every command's serialized shape do: change either and every saved board fails its checksum (section 2, “Hash over sorted keys”).

PAIR C / 3Replay is what gives a v1 board its meaning

crates/engine/src/lib.rs:107-119, 57-60Rust
pub fn replay(&mut self, commands: Vec<Command>) -> Result<()> {
    if commands.len() > MAX_COMMANDS { // 256
        return Err(Error::new("capacity", …));
    }
    let mut candidate = Self::default();7
    for (index, command) in commands.into_iter().enumerate() {
        candidate.execute(command).map_err(|e| Error::new(
            "replay_failed", format!("step {index}: {}", e.message)))?;
    }
    *self = candidate;9
    Ok(())
}

// execute, Command::Add
let title = Title::try_from(title.as_str())8

let id = next.add(title).map_err(|e| Error::new("capacity", e))?;

7Ids come from replay, not from the file. Every load starts at next_id 1, and undo restores next_id with the board, so ids are reused: replaying add A, undo, add B, complete 1 completes B. Change allocation or undo and old complete/remove commands fail as replay_failed or silently hit a different task.
8Domain rules run again on every load. Title trimming and validation and the 64-task cap apply at replay time; a failure comes back as replay_failed “step N: …” with the inner code folded into the message. Tightening any rule strands boards that obeyed the old one, so the rules are part of what “v1” means.
9All or nothing, history included. The candidate replaces the live session only after the last step, and revision and can_undo come back because undo is journaled (store_tests roundtrip_preserves_state_journal_and_undo undoes after a reload).

Confirm what must be preserved

  
Each line is a claim this map makes about v1. Mark it confirmed or wrong; anything you leave alone goes back as unreviewed. The reply below updates as you go.

  

    
1. A v1 file is a journal replayed under v1 rules. Titles, ids, next_id and undo history are re-derived on every load; nothing derived is stored.Pair A note 2 · Pair C

    
2. The v1 checksum is sha256 of compact {"schema_version":1,"commands":[…]} in that field order with today's command shapes, compared as exact lowercase hex.Pair A note 3 · “Hash over sorted keys” · store.rs:24, 132

    
3. Any encoding of the same data is the same v1 board: whitespace, key order and escapes in the file do not matter.“Same board, reformatted”

    
4. v1 files keep today's gate order and codes: storage_io, capacity, invalid_store, version, corrupt_store, then capacity/replay_failed, and no failure touches the live session.Pair B · section 2

    
5. Shipped builds are already fixed: they answer any file with a new command, field or key as invalid_store, and overwrite it on the next save. Only builds from this change on can report a newer file as version.Pair B notes 4–6

    
6. Free to change: load error message text (DRIVER.md promises a code and a message, not the wording) and the private Journal/Envelope types, as long as v1 re-serialization stays byte-identical.store.rs:10-21 · DRIVER.md

  


  

    Pin v1 before the format changes?
    
Nothing pins v1 today. corrupt_future_and_oversize_files_do_not_change_live_state asserts only is_err() and unchanged state; no test asserts invalid_store, version or corrupt_store, and no fixture holds v1 bytes. Changing v1 hashing in writer and reader together, or reordering the gates, would pass today's suite.
