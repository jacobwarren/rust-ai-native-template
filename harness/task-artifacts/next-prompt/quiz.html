What changed in cargo xtask task-artifact next and verdict, why it is shaped this way, and six questions to pass before merging. A retry draws different questions.

The prompt

1 · Context and intuition

Every task page is written by a fresh subagent that knows only what the orchestrator hands it. On main, next named the page and which subagent to start, but not what to say. The orchestrator looked the prompt up in docs/ARTIFACTS.md, filled its braces, found the exemplar, and retyped the reviewer's findings into verdict --notes TEXT. The blindspot pass found past tasks filling {task} three different ways.

The intuition: the router picks the same steps as before; only their says were reworded. One call at router.rs:351, handover::attach(), then adds handover and unfilled to the four steps that start a subagent: author, build, review and rewrite. Commit, best and complete steps return before the guide is read. The text is built from the guide's prompt table, compiled into the binary, and an optional prompt object in the task record. On the way back, verdict --notes - takes the reviewer's reply from stdin.

3 · Three behaviours a diff skim won't show you


    

      
01Braces are filled per prompt, from record fields, and a gap never blocks

      

        
What
fill() looks only at the braces the page's own prompt contains, and names a gap by the record field it needs, not by the brace. {task} is read from task in the blindspot prompt and from task_noun everywhere else. A value counts as given only if it is non-empty after trimming and not wrapped in <…>, the shape of the ticket stub's placeholders. A gap leaves the brace in the text, is listed in unfilled, and puts the fill note in front of the say; the step and its exit code are otherwise unchanged. The fields each prompt reads:
          
blindspots task, areainterventions probleminterview task_nounreference reference, task_nounplan task_nounimplementation task_nounbuy-in task_nounquiz none

        
Why
“I'm about to {task}” needs a verb phrase, “shipping {task}” a noun phrase, and the ticket ruled out rewording the prompts. next only advises, and six of the seven task records have no prompt object. The note leads because a review say ends with the command to copy.

        
Where
handover.rs:103 given() :110 fill() :243–251 task_record.rs:52–61 Prompt tests missing_values_stay_as_braces

      

    


    

      
02The guide is part of the binary

      

        
What
include_str!("../../docs/ARTIFACTS.md") compiles the guide in, and rows() reads its table by the new File column, refusing it unless the eight pages appear in page order. cargo xtask is an alias for cargo run -p xtask, so every call rebuilds against the guide on disk. On a clean copy whose step was the quiz author, swapping the buy-in and quiz rows gave:

$ cargo xtask task-artifact next --task next-prompt
{"error":"docs/ARTIFACTS.md's prompt table must list blindspots.html, interventions.html, interview.html, reference.html, plan.html, implementation.html, buy-in.html, quiz.html in its File column, in that order","ok":false}
exit 1

        
Why
One copy of the prompts cannot drift from the guide people read, and a swapped row is an error rather than one page quietly receiving another's prompt.

        
Where
handover.rs:14 :32–65 rows() :262 next_prompts_match_the_artifacts_guide .cargo/config.toml

      

    


    

      
03Findings reach the rewrite through stdin

      

        
What
main.rs compares the --notes value with "-"; on a match piped_notes() reads stdin, otherwise the value is stored as given. The rewrite hand-over carries the page's last log row's notes after “Round N findings; address every one:”. The same reviewer reply passed inline through bash on a clean copy:

$ … --findings 1 --notes "REVISE 1. `page_step` drops $PAGE. FINDINGS: 1"
bash: line 1: page_step: command not found
  "ok": true,
    "notes": "REVISE 1.  drops . FINDINGS: 1",

        
Why
The shell ran the backticks and expanded $PAGE before xtask started, so verdict could not tell. Piped bytes are never parsed by the shell; the Rewrite tab shows the same reply arriving intact.

        
Limits
piped_notes() refuses more than 64 KiB (counted on bytes before decoding), input that is not UTF-8, and input that is only whitespace, each with exit 1 and before anything is written to the log.

        
Where
main.rs:50–68 main.rs:129 handover.rs:195–199 tests verdict_reads_full_notes_from_stdin

      

    

  


  

    

      
What this leans on, and what it leaves open

      
Records stay strict. Task and the new Prompt are both deny_unknown_fields (task_record.rs:27, :52), and schema_version stays 6. Main's Task has no prompt field. Only harness/tasks/next-prompt.json carries the object.

      
Two open decisions. The reviewer's reply format now lives in one hand-over line, “PASS or REVISE on the first line, numbered findings, and a last line FINDINGS: N” (handover.rs:204), while review-artifact's SKILL.md:64 still says a PASS is one sentence: where it should live is Decision A. Nothing compares the piped text with that format or with --findings: whether verdict should check it is Decision B.
