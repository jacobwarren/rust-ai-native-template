The skill's description is not valid YAML to a strict parser

Plan said
Choice ④ shows the frontmatter as drafted: description: Investigate this repository before changing it: find the requested behavior's entry point, …. Its wording was left to you.
Code does
DOC008 reads only the name: line (checks.rs:216-222), so nothing parses the description. The : after "changing it" starts a second mapping inside a plain YAML scalar.
Caught by
yaml.safe_load on each skill's frontmatter. author-artifact, review-artifact and write-ticket parse. investigate fails with mapping values are not allowed here, and so does the existing add-product-command, for the same reason. Codex's own skill validator calls yaml.safe_load and would report "Invalid YAML in frontmatter". The hosts are more lenient. Codex 0.161's codex debug prompt-input lists - investigate: Investigate this repository before changing it: find … in full, and Claude Code's frontmatter parser has a fallback that quotes such values (read in its bundled source, not run).
Conservative fix
Put the description in double quotes in both copies. Tried in the clean copy, it parses as YAML, cargo xtask docs stays ok because the body is untouched, and Codex lists the same text. add-product-command is outside this ticket. Quoting it as well is a one-line change and optional.

#Plan saidCode does, and what was chosen
2 · settledA2: --model must be at most 64 characters (64 accepted).model.len() > 64 counts bytes. 33 × é (66 bytes) is refused with "64 characters", and 32 are accepted. A control character such as \x01 passes the no-whitespace rule. Kept as is: hosts name their models in ASCII, where bytes and characters agree, and the byte limit only errs on the strict side.
3 · settledA2: --findings two and -1 are refused.Both are refused, as are 4294967296 and " 2". Rust's u32 parse also takes +3 and 007 and stores 3 and 7. Kept as is, because the row holds the number and no reading of it is lost.
