The blindspots

Landmine01

In CI, the order check reads zero commits and passes

The CI handoff step runs actions/checkout with no ref: (.github/workflows/ci.yml lines 21–24). On a pull_request event that checks out GitHub's test merge commit, whose first parent is the base. history::commits walks base..HEAD --first-parent --no-merges (history.rs:48). It skips the merge and stops at the base, so the list is empty. order() then returns Ok when it finds no code commits (artifacts.rs:157–159).

ProbeA branch commits code, then all eight pages. At the branch tip, complete fails: "blindspots.html must be committed before the first product-code commit". After git merge --no-ff onto the base, git log --first-parent --no-merges base..HEAD prints nothing and complete returns ok=true with no errors. The existing test merged_target_commits_do_not_count_as_task_code covers only the opposite case, where the target is merged into the task branch.
Why it bitesLocal runs enforce order. The one gate every PR passes through does not. I reproduced this with a local merge commit, not on GitHub.
Make the CI handoff read the PR's own commits: check out pull_request.head.sha, or walk HEAD^2 when HEAD is a merge whose first parent is the base. Add a test that builds a GitHub-style merge commit with pages committed after code and expects a failure.
Landmine02

Order is checked only when a task says it is complete, and this PR takes the other route

completion::task passes task.status == Status::Complete as the final stage (completion.rs:20). check calls order() only in that case (artifacts.rs:105). A partial handoff checks only that five files exist. order() reads only commits since the base. Once the code has merged, a later branch that only flips the status has no code commits to compare against.

ProbeA partial task commits code, then discovery pages. Its handoff returns ok=true. In another run the code and all eight pages, written after it, merge as partial. A later branch that only flips the record to complete passes complete with ok=true and no errors. This PR's record is "status": "partial" with discovery "written after the code".
Why it bitesSplitting a task into "partial now, complete later" is the normal shape of multi-PR work, and it erases the ordering rule without anyone meaning to.
Decide whether commit order belongs to the task or to the branch. If it belongs to the task, run order() on partial handoffs too. When a record flips to complete, read commits back to the record's first commit, not to the merge base.
Missing concept03

The gate sees a style tag, not a page

verify() accepts any file that contains the marker string (artifacts.rs:131). The test fixture's pages, about 145 bytes each (a doctype, the style block, one paragraph; tests/support/mod.rs:119–127), pass completion. The reviewer's verdict goes into review.verification, which review_errors checks only for being non-empty (task_record.rs:136–137, 151; tracking.rs:47).

ProbeFive pages whose whole content is the 36-byte marker <style data-artifact-foundation="1"> let a README change pass task-artifact check and handoff with ok=true.
Why it bitesThe trial's record credits reviewers, not the gate, with its two code defects: save overwriting an oversized board, and a writer below the oldest readable format. When time is short, the cheapest passing page is the 36-byte marker alone.
Treat the gate as a reminder, not evidence. Report each page's reviewer verdict and one finding it caught, and explain any page under half its exemplar's size.
Missing concept04

Every PR owes five pages, or rides on someone else's task

handoff compares every file in the checkout (completion.rs:124). Any change at all needs an added or updated task record (:161). The record must be schema 6 (task_record.rs:124), and its check requires the five discovery pages (artifacts.rs:94–104). The guide says "a small task gets a smaller page"; the code has no lighter path.

ProbeA one-line README change fails with "changed source requires an added/updated task reconciliation record". With a new record it fails with "missing blindspots.html". With five stub pages it passes. Editing only the remaining text of a merged partial task also passes, with no new pages.
Why it bitesThe journal-versioning trial wrote 334,651 bytes over eight pages (4,004 lines) for 388 inserted lines in 14 files (13 under crates/engine, plus docs/DRIVER.md; task record excluded). Its record's review.verification: six pages passed review first time, two after one rewrite each. A typo fix pays the same, or rides an open task for free.
Before the next change, tell me which PRs are exempt (docs-only, dependency bumps, typo fixes) and whether unrelated work may ride an open task record. Make handoff enforce both.
Convention05

administrative() lists six paths, and everything else is product code

Only harness/task-artifacts/, harness/tasks/, harness/transitions/, docs/plans/, harness/docs.json and harness/gaps.json are exempt (artifacts.rs:33–43). Every Markdown doc, README.md, AGENTS.md, examples/, scripts/ and .github/ count as product code, and so does harness/readiness.json, which COMPLETION.md tells you to edit in the same change. By this rule, 39 of this PR's 42 files are product code.

ProbeA commit of docs/GUIDE.md before the discovery pages fails completion: "blindspots.html must be committed before the first product-code commit".
Why it bitesSketching the doc first, the natural start for a docs-led change, trips the order rule, and the Codex hook blocks that edit before discovery.
Before committing anything, list every path you will touch and say which ones administrative() counts as product code.
Landmine06

The pre-edit guard covers one tool on one host

The only hook config, examples/codex-artifact-hooks.json, guards edits by ^apply_patch$ only (artifact_hook.rs:15–19). Its Stop hooks run agent-stop, which sees any writer but checks only the named task (completion.rs:232). There is no Claude Code hook config. guard() checks the pages exist at HEAD, not that they preceded the code (artifacts.rs:192–206). Both hooks read HARNESS_TASK_ID, fixed per session.

ProbePartial TASK-1's pages and code are in main. A new branch, still naming it, edits implementation.rs (event.json patches it): 
$ xtask artifact-hook --task TASK-1 < event.json
  ok:true
$ xtask task-artifact guard --task TASK-1
  ok:true
$ git commit -qam 'new work'
$ xtask agent-stop --task TASK-1 --base main --report target/report.json
  ok:true, task errors []
$ xtask handoff --base main
  ok:false "changed source requires an added/updated task reconciliation record"
Editing only the record's remaining line then passes handoff (04).
Why it bitesShell writes, cargo fmt and the Claude host that built this PR all bypass the pre-edit guard. Only handoff, which CI runs, looks at the diff, and blindspot 01 shows CI does not check order.
Tell me the next agent's host and tools, and set HARNESS_TASK_ID to the new task. Unless it is Codex apply_patch, there is no pre-edit guard: run cargo xtask task-artifact guard yourself before the first code commit.
History07

Schemas 3–5 never shipped, and an old record can't be touched in passing

Main accepted schema 1–2 and required 2. The experiment commits earlier on this branch added 3, 4 and 5. This PR reads 1–6 and requires 6 (task_record.rs:67, 124). coordination skips the page check below 6 (completion.rs:218–220). completion-gate.json is schema 2 and complete. Editing it puts it through handoff, which then demands an upgrade to schema 6 and eight pages for work that merged long ago.

ProbeA schema-5 partial record with code passes coordination with ok=true. handoff rejects it: "Upgrade this active task to schema_version 6…" and "missing blindspots.html".
Why it bitesThe PR's rollback note says records below schema 6 are unaffected. That holds only while nobody edits them.
Upgrade an old task record in its own commit, and tell me which pages it then needs.
