Deviation 1 of 3B1

One positive predicate, ceremony_skill(path), replaces free_skill(host, path)

The plan said
free_skill(host, path) returns true for a skill outside the ceremony. protected() negates it under .claude/skills/ and forces_standard negates it under .agents/skills/ (plan A2, marks 2–4).
The code showed
Three callers need the same answer: protected() (transitions.rs:83-86), forces_standard (size.rs:27) and the new docs check (checks.rs:282). Each one must treat a loose file such as .claude/skills/README.md as ceremony. With a "free" predicate, each caller would have to repeat that negation.
Conservative choice
ceremony_skill (transitions.rs:73-81) covers both hosts. It returns true for the three names and for any file outside a skill folder (None => true, line 78). A path it doesn't recognise costs a standard task and never gets through free. A new test, only_ceremony_skills_stay_protected_under_claude, pins this behaviour and shows that author-artifact-notes/ stays free: names are matched whole, never by prefix.
Revisit
Nothing is pending. A skill outside the ceremony can never put a file directly in skills/.

Deviation 2 of 3B1

Skill names compare without case on every checkout

The plan said
Blindspot card 03: the guard's list must "go through lower() like PREFIXES_CMP". lower() folds case only when core.ignorecase is set (agent-hook.sh:93-95).
The code showed
Nothing in xtask/src reads core.ignorecase (grep). A conditional fold in the guard would have no Rust counterpart, so on a case-sensitive checkout the guard and handoff could disagree.
Conservative choice
Both sides always fold: eq_ignore_ascii_case in Rust (transitions.rs:77) and tr in the guard (agent-hook.sh:147). On Linux, a separate Author-Artifact/ folder therefore counts as the ceremony skill, which is stricter and never looser. Captured on this macOS checkout: an edit to .Claude/Skills/Author-Artifact/SKILL.md gets the receipt note.
Revisit
Only if someone wants a free skill whose name differs from a ceremony skill by case alone.

Deviation 3 of 3B2

A bare folder under .claude/skills/ gets the guard note for every skill, free or not

The plan said
Footnote 5: the guard matches only .claude/skills/*/*. A bare rm -r .claude/skills/author-artifact falls through to the .claude/ prefix and keeps its note.
The code showed
From the name alone, the guard can't tell a one-segment path such as investigate (a folder) from README.md (a loose file). After an rm, there is nothing left on disk to check.
Conservative choice
Any one-segment path under .claude/skills/ ranks as policy (agent-hook.sh:146). Captured: rm -r .claude/skills/investigate gets the receipt note even though handoff won't ask for a receipt, and mv .claude/skills/investigate .claude/skills/author-artifact names the source instead of the destination. Extra notes are safe because the note is only advisory and handoff reads git's list of files.

If the spurious note gets in the way, check a one-segment name without an extension against CEREMONY_SKILLS.

What the build changes about the story

  1. Handoff decides; the guard is coarser in both directions. Any one-segment path under .claude/skills/ gets a note, and rm -r .claude never does. Say this in the buy-in doc instead of promising that the two always agree.
  2. Membership is a folder name in one list, compared without case. A skill that needs hooks, tool grants or scripts joins CEREMONY_SKILLS in the same change. Until it does, DOC011–DOC013 refuse it, and the parity test keeps the guard's copy equal.
  3. Before completion: name .agents/skills/author-artifact and .claude/skills/review-artifact in the tier test, record the rm -r .claude discovery, and write the receipt over the ten protected files last.
