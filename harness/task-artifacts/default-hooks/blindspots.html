Blindspots in turning the hooks on by default

The prompt
I'm about to ship project hooks for Claude Code and Codex that are on by default (feedback after each edit, a guard before edits to golden baselines and protected policy files, the completion gate at stop, and permission rules for dependencies, merging and force-pushing) in this Rust harness template's xtask, scripts and agent configuration. Do a blindspot pass: find my unknown unknowns in this part of the codebase, explain each one with the code that proves it, and tell me how to prompt you better for the implementation.

From scripts/, seven xtask/src modules, the docs and both hosts' hook references. Probes ran in a clean clone; host behaviour marked tested ran in Claude Code in a throwaway project.

What you're walking into

It looks like two JSON files around scripts that already exist, but the stop script blocks every turn that names no task, "protected" means "needs a receipt", the harness prints the one cp that re-blesses a golden, the feedback cargo check writes a protected file, and any stray file makes the tree look changed.

The blindspots

Landmine01

The stop gate you're turning on blocks every stop that doesn't name a finished-enough task, including "what does this do?"

scripts/agent-complete.sh:4–7 exits 2, "keep working", when HARNESS_TASK_ID or HARNESS_BASE is unset. On by default, that fires at the end of every turn in every clone, because nothing in the repository sets them.

Setting them doesn't help mid-task. agent_stop (completion.rs:232) runs task(), which reports every empty review.* answer (completion.rs:36, task_record.rs:122) and every missing discovery page, even on a partial record (artifacts.rs:91–95, "Discovery pages are always required"). Against this task's own partial record, before any page was committed:

$ env -u HARNESS_TASK_ID -u HARNESS_BASE bash scripts/agent-complete.sh
Set HARNESS_TASK_ID and HARNESS_BASE before using the completion hook.   exit 2
$ HARNESS_TASK_ID=default-hooks HARNESS_BASE=HEAD bash scripts/agent-complete.sh
(errors array; each line below is cut after its question)
"review.acceptance: Did any assigned acceptance criterion remain unmet? …",
"review.verification: Did checks reveal a pre-existing problem or unresolved failure? …",
"review.assumptions: Did this task rely on an unverified assumption? …",
"review.coverage: Did you discover a material missing test, recovery path or platform check? …",
(plus one "task HTML artifact: missing …" line)                       exit 2
$ cargo xtask handoff --base HEAD        # clean tree, no task named
"errors": [], "ok": true, "tasks": []                                  exit 0

Only handoff has a "nothing changed, nothing owed" path (completion.rs:160). The base must be a fresh remote ref: a stale local main counts already-merged commits as this branch's changes.

Why it bitesClaude Code overrides a Stop block after eight consecutive continuations, but "the count of consecutive continuations resets each time Claude calls a tool" (hooks reference, "Stop input"), so an agent that reacts by running tools never reaches the cap. onFailure "has no effect" on Stop and SubagentStop. The example config also wires SubagentStop, so the author and reviewer subagents this repository requires get sent back too.

Missing concept02

"Protected" means "needs a receipt", not "never edit", and the two hosts can't share one decision table

transitions::protected() (transitions.rs:37–61) covers the prefixes xtask/, .github/, scripts/, .cargo/ and harness/goldens/, plus harness/{config,readiness,tracking,workflows,scenarios}.json, the root Cargo.toml and Cargo.lock, docs/{PRODUCT,READINESS,COMPLETION}.md and AGENTS.md. Its job is to make CI ask for a rationale (transitions.rs:111–127), not to forbid edits. This task must itself edit scripts/, xtask/ and docs/COMPLETION.md, and 11 of the 17 non-merge commits on main touch the list.

Goldens differ in kind: AGENTS.md:70–71 says never regenerate them to make an implementation pass, and golden.rs:39 allows updates only as "an explicit reviewed source change". That is an ask. The specs that produce them, workflows.json and scenarios.json, sit in the same list; card 03 edits one. A committed Claude deny can't be lifted: "if a tool is denied at any level, no other level can allow it" (permissions reference, "Settings precedence"). Codex parses permissionDecision: "ask" but "marks the hook run as failed, reports the error, and continues the tool call" (Codex hooks page, PreToolUse), so on Codex an ask guard is an allow.

Nothing under .claude/ or .codex/ is protected, so a later PR can delete the guard without a receipt. Codex is stricter: "new or changed hooks are marked for review and skipped until trusted", so its hooks stay off in a fresh clone until someone trusts them in /hooks.

Why it bitesDeny the whole list and most of the harness's own history, this task included, couldn't have been written; allow it and the guard adds nothing CI didn't already do.

Landmine03

The harness hands the agent the exact cp that re-blesses a golden, and an Edit|Write hook never sees it

When a workflow's result differs from its baseline, golden::compare writes the actual result to a candidate file and prints its path (golden.rs:35–36, workflows.rs:130). Copying it over the baseline is all it takes:

$ sed -i '' 's/"Keep"/"Kept"/' harness/workflows.json; cargo xtask workflow
"baseline": "harness/goldens/kept.json",
"candidate": "$PWD/target/harness/runs/1793810325969804000-48271/rejected-edit-0-5.candidate.json",
"error": "baseline mismatch",
(clone path shown as $PWD; three more candidates follow for other cases that share kept.json)
"ok": false                                                                exit 1
$ cp target/harness/runs/1793810325969804000-48271/rejected-edit-0-5.candidate.json harness/goldens/kept.json
$ cargo xtask workflow
"ok": true                                                    exit 0, golden rewritten by Bash
$ cargo xtask gaps --base HEAD
"errors": ["missing exact transition rationale: policy"],
"protected_files": ["harness/goldens/kept.json", "harness/workflows.json"]   exit 1

A PreToolUse matcher filters on tool_name, so an Edit|Write hook is never called for this. Claude's Edit(path) deny rules do reach "file commands Claude Code recognizes in Bash, such as cat, head, tail, sed, and tee", but not "arbitrary subprocesses" (permissions reference). Tested with Edit(/goldens/**) denied and each command explicitly allowed:

Why it bitesThe guard exists to stop "make the test pass by changing the expectation", and the shortest route to that is one it can't see. The stop gate then asks for a policy receipt, which the same agent can write.

Landmine04

The post-edit cargo check adds dependencies to Cargo.lock, and the permission rules match spellings, not effects

protected() holds the root Cargo.toml by exact name, not crates/*/Cargo.toml. Adding a workspace dependency to a member manifest is an ordinary edit, and a plain cargo check then rewrites the lockfile, which is protected:

# add  sha2.workspace = true  under [dependencies] in crates/app/Cargo.toml
$ cargo check -q --locked -p starter-app
error: cannot update the lock file $PWD/Cargo.lock because --locked was passed to prevent this   exit 101
$ cargo check -q -p starter-app && git status --short
 M Cargo.lock                                  written by the feedback check
 M crates/app/Cargo.toml
$ cargo xtask gaps --base HEAD
"errors": ["missing exact transition rationale: policy"], "protected_files": ["Cargo.lock"]

Only the cargo xtask alias is locked (.cargo/config.toml:2), not plain cargo. A Bash(cargo add *) rule never sees a manifest edit, and the push and merge rules are as literal. codex execpolicy check with prefix rules for cargo add, git push --force|-f and gh pr merge:

cargo add serde                          prompt
git push --force origin x                forbidden
gh pr merge 3                            forbidden
git push origin x --force                no rule matched
git push origin +x                       no rule matched
git push --force-with-lease origin x     no rule matched
git -C . push --force                    no rule matched
gh api -X PUT repos/o/r/pulls/3/merge    no rule matched

Claude's reference says the same: Bash(git push *) does not match git -C . push origin main. "Merging" needs a definition too. Completion reads the branch with --first-parent --no-merges (history.rs:56–57), which expects merges from main into the branch; what AGENTS.md:64–66 reserves for the owner is merging the PR.

Why it bitesThe feedback hook makes the stop gate demand a receipt nobody meant to need, and the dependency rule suggests new crates are reviewed when the real gate is still CI's architecture check.

Landmine05

A broken hook either lets everything through or blocks the fix, depending on its exit code

For Claude Code, an exit code other than 0 or 2, a timeout, or a script that won't start is a non-blocking error and "the action goes ahead" (hooks reference, "Exit code output"). The existing edit wrapper takes that path when its variable is unset, and since it runs target/debug/xtask without building it (agent-artifact-write.sh:7), a fresh clone blocks for the wrong reason. Fed a patch that only touches harness/task-artifacts/:

$ echo '{}' | env -u HARNESS_TASK_ID bash scripts/agent-artifact-write.sh
scripts/agent-artifact-write.sh: line 4: HARNESS_TASK_ID: Set HARNESS_TASK_ID for this session
                                                              exit 1 → edit proceeds
$ HARNESS_TASK_ID=default-hooks bash scripts/agent-artifact-write.sh < patch.json
"scope": "Artifact/administrative edit; source boundary not crossed"   exit 0
$ mv target/debug/xtask elsewhere; HARNESS_TASK_ID=default-hooks bash scripts/agent-artifact-write.sh < patch.json
scripts/agent-artifact-write.sh: line 7: $PWD/target/debug/xtask: No such file or directory
Write and commit the five discovery pages (docs/ARTIFACTS.md) before editing product code. Artifact-only patches remain allowed.
                                                              exit 2: artifact-only patch blocked

Claude Code's "onFailure": "block" (v2.1.295 and later) makes a crash or timeout block. Tested with a Bash hook that only runs exit 1: without the field the cp ran; with it, it was blocked. That is the opposite trap for a guard built from the tree it guards: once an edit breaks xtask/ (error: this file contains an unclosed delimiter), cargo xtask exits 101 on every call, and the guard blocks the edit that would fix it. The Codex hooks page documents no onFailure equivalent.

Why it bitesFail-open turns a missing variable into a silent "allowed"; fail-closed turns a typo in xtask/ into a session that can't edit its way out. Only a path check that never calls Cargo avoids both.

Landmine06

Any untracked or ignored file makes the tree look changed, and $CLAUDE_PROJECT_DIR points at the wrong tree in a worktree

handoff fingerprints the tree with history::current, which walks it via repo::files. That skips only .git, target, .DS_Store, __pycache__, *.pyc and .env* (repo.rs:22–25) and never consults .gitignore. One scratch file removes card 01's "nothing changed" path:

$ echo hi > zzz.txt && cargo xtask handoff --base HEAD
"errors": ["changed source requires an added/updated task reconciliation record"], "ok": false   exit 1
$ rm zzz.txt; echo '{"permissions":{"allow":["Bash(ls:*)"]}}' > .claude/settings.local.json
$ git status --short          # empty here only because of a global git exclude; this repo's .gitignore has no rule for it
$ cargo xtask handoff --base HEAD
"errors": ["changed source requires an added/updated task reconciliation record"], "ok": false   exit 1

Claude Code writes that file on the first "Yes, and don't ask again" (settings reference) and puts claude -w worktrees under .claude/worktrees/, where ignoring them in .gitignore doesn't help. Hook paths have a related trap: $CLAUDE_PROJECT_DIR "still points at the project root where the session started" after Claude enters a worktree, while the event's cwd follows Claude (hooks reference, "Reference scripts by path"). "$CLAUDE_PROJECT_DIR"/scripts/agent-complete.sh runs cd "$(dirname "$0")/.." and checks the main checkout, not the worktree being edited.

How should the Stop hook decide that nothing changed?

Checked and fine

  • A cold cargo build -p xtask took 4.7 s and a warm cargo check --locked -p starter-app 0.08 s, well inside a 30 s hook timeout. The margin shrinks as an adopted product grows, and each worktree builds its own target/.
  • "User cancellation must remain possible" (docs/COMPLETION.md:165) holds: Claude's Stop "does not run if the stoppage occurred due to a user interrupt", and Codex's Interrupt hook "can't prevent the interruption". Its neighbour, "no vendor configuration is silently installed", doesn't; the prompt covers that rewrite.
