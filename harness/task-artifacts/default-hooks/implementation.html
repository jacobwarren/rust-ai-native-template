Deviations

Deviation 1 · slice 2 · stricter

A shell write gets the same tier as an edit, not only the golden tier

Plan said
A4: a Bash command is a golden write, a mention or a merge. The test table expects a heredoc into xtask/tests/hooks.rs that quotes a goldens path to print {}.
Code does
The shell parser's destinations go through the same decide() as edit paths (scripts/agent-hook.sh:269–275). sed -i s/a/b/ harness/config.json asks on Claude and is refused on Codex. A shell write to any protected path gets the receipt note.
Why
The allowlist ask is an Edit(…) rule (.claude/settings.json:7), and no shell command reaches an Edit(…) rule. Blindspot 03 showed the same for cp onto a golden. With goldens alone tiered, sed -i could widen a dependency allowlist without asking.
Conservative choice
Each destination gets its strictest tier, exactly as for an edit. The test's heredoc fixture moved to crates/app/tests/fixture.rs (xtask/tests/hooks_guard.rs:202).
Revisit
Notes never block. If shell writes to xtask/ make them noisy, narrow shell writes to golden and allowlist.
Deviation 2 · slice 2 · stricter

The error trap reaches every function, so paths travel as strings, never through a pipe

Plan said
D: set -u and trap '… exit 2' ERR, never bare set -e.
Code does
set -uE in both scripts (agent-hook.sh:7, which now also has -f, see Deviation 6; agent-complete.sh:11). Paths go to decide() one per line through a here-doc (agent-hook.sh:134–155).
Why
Without -E, functions don't inherit the trap. In a repro, a false inside a function let the script carry on to exit 0, which fails open. The first version with -E piped paths into decide. The pipe ran it in a subshell, so its deliberate exit 2 became a failed pipeline in the parent, and the trap added "internal error" to every block.
Conservative choice
The trap stays fail-closed everywhere, and every deliberate exit runs in the main shell. Slice 3 follows the same rule: try() captures Cargo's status with && code=0 || code=$? (:295–304).
Revisit
If someone brought the pipe back, no test would fail, because a block still exits 2 with its reason first. The trap also left a gap: set -u aborts on an unset variable without running it. Deviation 7 closes that gap.
Deviation 3 · plan corrected before slice 1 For you

The architecture check also runs after Rust edits, not only after manifest edits

Plan said
In the version you approved, A5 ran xtask architecture only after Cargo.toml, Cargo.lock or harness/config.json edits, because the check "reads only cargo metadata".
Code does
A .rs edit also sets arch=1 (agent-hook.sh:323–324). This is Q6 as you first answered it.
Why
The reason in the plan was false. architecture() reports SIZE001 for any .rs file over 400 lines (xtask/src/checks.rs:76–90). It caught this task: the first check fast failed on "SIZE001 xtask/tests/hooks.rs: 610 lines exceeds 400".
Conservative choice
Run the check after Rust edits too. A 450-line file now fails at edit time, not at CI.
Deviation 4 · slice 3 · stricter

The post-edit check compiles tests too

Plan said
A5: cargo check -q --locked -p PKG.
Code does
It adds --all-targets --message-format short (agent-hook.sh:334, :337).
Why
An edit under crates/*/tests/ resolves to its crate, but a plain cargo check never compiles integration tests, so their errors would go unreported. On a type error, the observed output names both the lib and the lib test targets.
Conservative choice
Check every target of the crate that was edited. A warm no-op edit takes 0.9–1.0 s.
Deviation 5 · slice 3 · caught by these notes, fixed

When xtask can't be rebuilt, the check now says so

Plan said
A5: when cargo build --locked -p xtask is refused, the older binary still runs, and "the report says it may predate this branch's xtask/ edits".
Code did
The first slice-3 version threw away the build's failure with || true and ran whatever binary existed, without comment. If there was no binary, it skipped architecture without saying so. These notes flagged both.
Code does
A failed build now sets built=0 (agent-hook.sh:341–342). If the check fails on the old binary, the report ends with the caveat (:345–348). With no binary at all, the report says "xtask architecture was not checked: xtask could not be built." (:349–351). post_edit_check_uses_the_built_xtask_when_the_lock_is_stale asserts both messages.
Conservative choice
Report the stale binary, as the plan said. Observed after adding rand to crates/app/Cargo.toml: the --locked error, then ARCH004 starter-app -> rand, then "(xtask could not be rebuilt, so this architecture result comes from an older binary that may predate this branch's xtask/ edits.)"
Deviation 6 · after slice 3 · fixed

A .. path is resolved, not refused

Plan said
D: "Paths outside the root pass, and .. is blocked." Slice 2 refused every path containing .. with "agent-hook will not judge a path containing '..'".
Code did
The rule refused ordinary writes outside the repository. The live guard blocked an agent's cp into a scratch directory. Run against the slice-2 script, cp x ../outside.txt exits 2 on both hosts. So does rm ../harness/goldens/kept.json from crates/, but with the traversal message rather than the golden one.
Code does
normalize() resolves . and .. by text alone, without reading the disk (agent-hook.sh:92–103). relative() resolves a relative path against the event's cwd and then strips the root spellings (:105–120). set -uEf turns globbing off, so a path splits on / safely. guard_reads_every_patch_path_and_blocks_what_it_cannot_read asserts the three new cases (hooks_guard.rs:70–86).
Conservative choice
The block existed to stop traversal tricks. Resolving the path keeps that protection, because the resolved path is what gets tiered. crates/../harness/goldens/kept.json and cp x ../<checkout>/harness/goldens/kept.json both ask on Claude and exit 2 on Codex, while cp x ../outside.txt passes, as plan D intended.
Revisit
Resolution never reads the disk, so a symlink inside the checkout that points at harness/goldens is not followed. That was also true before.
Deviation 7 · after slice 3 · fixed

A guard bug now blocks on Codex too

Plan said
D: the ERR trap turns any internal failure into exit 2. For a crash or timeout, the plan relied on Claude Code's onFailure: "block", and accepted that Codex fails open.
Code did
set -u aborts on an unset variable without running the ERR trap. With an echo "$undefined_variable" injected, the slice-2 guard exits 1 with "unbound variable", and bash -c exits 127. Codex lets the call through on any exit other than 0 or 2. Claude Code's onFailure was the only thing catching this kind of bug.
Code does
An EXIT trap turns every exit other than 0 or 2 into exit 2 with "internal error" (agent-hook.sh:9–11). With the same injection, the guard now exits 2 on both hosts, under Homebrew bash 5.3 and macOS /bin/bash 3.2. guard_fails_closed_on_an_internal_error asserts this (hooks_guard.rs:272–290).
Conservative choice
Fail closed. Only a guard that cannot start or times out still passes on Codex, as the docs now say.
Found by CI
The PR's macOS job runs macOS /bin/bash 3.2, where set -E runs the ERR trap inside a $(…) even when the caller guards it with ||. A refused claim in agent-complete.sh was reported as "could not run (exit 2)", and the guard printed a stray "internal error" outside a checkout. agent-complete.sh drops -E (it has no functions), and the guard's two git probes end in || true inside the substitution. Local runs had used Homebrew bash 5.3, which does not do this.
Revisit
agent-complete.sh keeps only its ERR trap. A stop gate that failed closed on its own bug would trap every turn, and a false claim it misses still fails at PR CI.
Deviation 8 · after review · owner's call

A PR merge asks on Claude Code; a force-push stays refused

Plan said
A4 and the settled defaults: deny gh pr merge, gh api …/merge and every force-push spelling, refused on both hosts, with literal deny rules in .claude/settings.json.
Code did
The guard exited 2 on both hosts for both, and deny rules cannot be lifted from settings.local.json. A Claude Code session could not merge even when the owner asked it to, as the owner had done for the previous PR.
Code does
The shell parser now tells a merge (gh pr merge, gh api …/merge) from a force-push. On Claude Code a merge gets permissionDecision: "ask", and the owner moved Bash(gh pr merge *) from deny to ask; Claude Code's auto-mode check refused the agent's own edit of that file as a self-permission change. A force-push is still refused on both hosts and its three deny rules stay. Codex, which cannot ask, refuses both, and its forbidden rules are unchanged.
Conservative choice
A merge is reversible and recorded, and AGENTS.md asks for the owner's say-so, which the prompt gives. A force-push rewrites history, so it stays a hard stop. Chosen by the owner after reviewing the PR.

What each slice taught

Slice 1 · tree and policy list

As planned

Two consts, and a host-local skip matched by full path

// xtask/src/repo.rs:18, :27–35
const HOST_LOCAL: [&str; 2] = [".claude/settings.local.json", ".claude/worktrees"];
            let rel = path.strip_prefix(base)?.to_string_lossy().replace('\\', "/");
                || HOST_LOCAL.contains(&rel.as_str())

The same name at docs/.claude/settings.local.json still changes source_sha256 and fails handoff (hooks_tree.rs:24–28). Slice 2 · the guard on both hosts

Discovery

On a real host, the note reached the agent building the guard

Claude Code picked up .claude/settings.json mid-session as soon as the file was in the working tree. On the build's own cat >> xtask/tests/hooks.rs, the agent read "PreToolUse:Bash hook additional context: xtask/tests/hooks.rs is a protected policy file…". The plan had left "how a host shows the note" untested. This settles it for Claude Code. Codex is still unobserved.

Discovery

Codex rules catch literal spellings; the guard catches the rest

$ codex execpolicy check --rules .codex/rules/default.rules -- CMD   (codex-cli 0.161.0)
cargo add serde               prompt
gh pr merge 3                 forbidden
git push --force origin x     forbidden
git -C . push --force         (no rule)       guard: exit 2 on both hosts
git push origin +x            (no rule)       guard: exit 2 on both hosts

The guard skips git's global -C/-c options. It treats --force*, a short cluster containing f, or a +refspec as a force-push (agent-hook.sh:181–191).

Discovery

One root, four spellings. Codex finds the script through Git

On macOS the event's cwd was /var/folders/… while Git reported /private/var/folders/…. relative() accepts four spellings (:87–120). Codex has no $CLAUDE_PROJECT_DIR, so its hook command locates the script with $(git rev-parse --show-toplevel) (.codex/hooks.json:9). Outside a checkout that becomes bash /scripts/agent-hook.sh, which exits 127, a non-blocking error. Codex fails open there, as interview Q2 expected.

Slice 3 · post-edit check and claims-only stop

As planned

The stop gate greps for a claim and lets the existing gate judge it

# scripts/agent-complete.sh:33, :45–47
CLAIM='"status"[[:space:]]*:[[:space:]]*"complete"'
  out=$($xtask complete --task "$id" --base "$base" --report "$report" 2>&1) && code=0 || code=$?
  if [ "$code" -eq 1 ] && [ "$(printf '%s\n' "$out" | head -n 1)" = "{" ]; then   # refused; else: could not run
$ stop, record partial                          → exit 0 in 0.43 s, no Cargo
$ stop, same record set to "complete"           → exit 2 in 2.7 s:
Completion claim refused: harness/tasks/default-hooks.json says complete, but the completion gate failed:
  "review.acceptance: Did any assigned acceptance criterion remain unmet? …"
  "task HTML artifact: missing buy-in.html; see docs/ARTIFACTS.md"

task_record::tests::stop_claim_pattern_matches_parsed_status runs the script's own CLAIM through grep against every record, in compact, pretty-printed and spaced JSON. A stub xtask that exits 101 turns a claim into "could not run (exit 101)" (hooks_stop.rs:46–64).

Discovery

CARGO_TARGET_DIR is how the check finds xtask, and it misled the tests

The check runs ${CARGO_TARGET_DIR:-$root/target}/debug/xtask (agent-hook.sh:340). The check fast profile sets that variable for each run, so two post-edit tests found the repository's real xtask instead of the fixture's stub. The helper now removes it (support/hooks.rs:27–28). In real use, the same variable is what points the hook at the right binary.

Discovery

Building hooks while they run

Once the Stop entry existed in the working tree, the stop gate ran at the end of every turn of the session building it. Every shell write to xtask/ or scripts/ printed the receipt note. To avoid the self-lockout that plan D warned about, both scripts were edited as scratch copies, checked with bash -n, and copied into place. One process slip: a test-splitting script deleted xtask/tests/hooks.rs before the split had worked, and the file was restored from Git.
